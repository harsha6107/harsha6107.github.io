## Context & The Cost/Reliability Crisis

Real-time data replication is deceptively easy to prototype and notoriously expensive to operate at scale. Our data platform needed to stream **436 production SQL Server tables** into a **493-table Snowflake Bronze layer** to power analytics, ML lead-time models, and enterprise B2B customer feeds.

Two critical bottlenecks stood in the way of a sustainable production cutover:

1. **Runaway Snowflake Compute (~48 Credits/Day)**: The legacy ingestion pattern executed continuous, near-per-record `MERGE INTO` statements as Kafka messages arrived. Because Snowflake bills virtual warehouses per active second (with a 60-second minimum), trickle writes prevented the warehouse from ever suspending—burning **~48 credits every single day** even during low-traffic hours.
2. **Silent Multi-Day Sync Gaps**: Whenever SQL Server underwent maintenance or AKS rotated worker nodes, Debezium tasks entered `FAILED` states without auto-healing, creating multi-day data blind spots.

## Architectural Approach

### 1. Debezium + Strimzi Kafka on AKS with Fail-Closed Watchdogs

I led the infrastructure provisioning and April 2026 production cutover using **Debezium**, **Strimzi Kafka on Azure Kubernetes Service (AKS)**, **Terraform**, **Helm**, and **GitHub Actions**:

- **Self-Healing Connectors & 15-Minute Lag Watchdog**: Enabled automatic Debezium task restart policies with exponential backoff and built a **15-minute replication lag and dead-letter queue (DLQ) watchdog** that pages on-call before transaction log retention windows expire.
- **Fail-Closed CI/CD**: Hardened Helm and GitHub Actions deployment pipelines to verify connector task status and partition offset advancement before marking any release healthy.

### 2. Cutting Snowflake Spend ~95% via Batched Micro-Drain MERGEs

Instead of trickling row-by-row `MERGE` queries against an always-on warehouse, we decoupled Kafka topic landing from Snowflake compute:

```sql
-- Idempotent batched MERGE deduplicating LSN ordering per scheduled drain window
MERGE INTO bronze.orders AS target
USING (
  SELECT *
  FROM staging.orders_cdc_stream
  QUALIFY ROW_NUMBER() OVER (
    PARTITION BY order_id
    ORDER BY __source_lsn DESC, __seqval DESC
  ) = 1
) AS src
ON target.order_id = src.order_id
WHEN MATCHED AND src.__op = 'd' THEN DELETE
WHEN MATCHED THEN UPDATE SET
  target.status = src.status,
  target.updated_at = src.updated_at,
  target.__cdc_lsn = src.__source_lsn
WHEN NOT MATCHED AND src.__op != 'd' THEN INSERT (order_id, status, updated_at, __cdc_lsn)
  VALUES (src.order_id, src.status, src.updated_at, src.__source_lsn);
```

- **Scheduled Drain Windows + Auto-Suspend**: Kafka buffers incoming CDC events into staging at zero warehouse compute cost. Scheduled drain workers spin up the warehouse, deduplicate multiple updates to the same primary key by highest Log Sequence Number (`__source_lsn`), merge **500K+ rows per run in ~1 hour**, route malformed records to a retry/dead-letter queue, and immediately auto-suspend the warehouse—**cutting Snowflake ingestion spend by ~95%**.

### 3. Taking Siemens Live on a Zero-Leak 74-Table CDC Feed

Enterprise customer **Siemens** required a direct **Snowflake-to-Snowflake CDC data share** covering **74 tables (~2.1M-row initial snapshot, with incremental changes applied twice daily)**.

- **Column-Level Pricing Redaction & Negative Testing**: Because internal distributor cost and margin columns reside in the same source operational tables, we constructed a projection boundary that physically withholds all internal pricing and multiplier attributes prior to the share view layer, locked Siemens to a dedicated read-only role with zero export escalation paths, and validated the boundary with an automated **negative-test suite** before leading the production cutover.
