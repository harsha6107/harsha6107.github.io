When streaming Change Data Capture (CDC) events from an operational relational database into a cloud data warehouse, the most expensive architectural mistake is treating a columnar analytical warehouse like an OLTP row store.

In early 2026, I led the production CDC pipeline streaming **436 SQL Server tables** into a **493-table Snowflake Bronze layer** using **Debezium** and **Strimzi Kafka on Azure Kubernetes Service (AKS)**, provisioned via Terraform, Helm, and GitHub Actions. Along the way, we cut Snowflake ingestion compute spend by **~95%** and hardened the pipeline against silent multi-day outages.

## Why Trickle MERGEs Burn ~48 Credits a Day

Snowflake virtual warehouses bill per active second with a 60-second minimum upon resume. Under a naive streaming consumer pattern, every small batch of CDC events arriving in Kafka immediately triggers a `MERGE INTO bronze.table` statement.

Because 436 operational tables emit at least a trickle of updates every minute, the ingestion warehouse **never suspended**. Running an always-on warehouse to apply trickle row-level merges consumed **~48 credits/day** (~$1,400–$1,800/month for a single ingestion tier) while spending 90% of its compute scanning micro-partitions to update a handful of rows.

## The Fix: Decoupled Stage Buffering + Batched LSN Micro-Drains

We separated **event durability** (which Kafka and cloud object staging handle for pennies) from **warehouse compute**:

1. **Zero-Compute Buffering**: Debezium captures SQL Server transaction log changes and streams them through Strimzi Kafka on AKS into staged micro-batches without waking a Snowflake warehouse.
2. **Scheduled Drain Windows (`QUALIFY ROW_NUMBER()`)**: During scheduled drain windows, an auto-resuming warehouse spins up, compacts all intermediate mutations per primary key using the highest SQL Server Log Sequence Number (`__source_lsn DESC`), merges **500,000+ rows per run in roughly an hour**, routes any schema-drift anomalies to a dead-letter queue (DLQ), and **immediately auto-suspends**.

```sql
-- Compaction + idempotent MERGE inside a scheduled drain window
WITH deduplicated_batch AS (
  SELECT
    payload:id::STRING AS id,
    payload:__op::STRING AS op,
    payload:__source_lsn::BINARY AS lsn,
    payload
  FROM bronze_staging.raw_cdc_events
  WHERE table_name = 'dbo.Orders'
  QUALIFY ROW_NUMBER() OVER (
    PARTITION BY payload:id::STRING
    ORDER BY payload:__source_lsn::BINARY DESC, payload:__seqval::BINARY DESC
  ) = 1
)
MERGE INTO bronze.dbo_orders AS tgt
USING deduplicated_batch AS src
ON tgt.id = src.id
WHEN MATCHED AND src.op = 'd' THEN DELETE
WHEN MATCHED THEN UPDATE SET tgt.record = src.payload, tgt.last_lsn = src.lsn
WHEN NOT MATCHED AND src.op != 'd' THEN INSERT (id, record, last_lsn) VALUES (src.id, src.payload, src.lsn);
```

This single architectural shift reduced Snowflake CDC compute consumption by **~95%** while improving end-to-end throughput stability.

## Closing Multi-Day Sync Gaps After AKS & SQL Server Restarts

Cost efficiency means nothing if replication silently halts during infrastructure maintenance. Previously, when AKS rotated worker nodes or SQL Server restarted during patching, Debezium connectors entered a wedged state, creating multi-day replication gaps.

We closed that reliability gap with three mechanisms:

- **Automatic Connector Task Restart**: Configured Strimzi/Kafka Connect task auto-restart with bounded backoff so transient socket resets heal within seconds.
- **15-Minute Lag & DLQ Watchdog**: Deployed an independent watchdog monitoring watermark age across active tables and dead-letter queue depth, alerting within 15 minutes of stagnation.
- **Fail-Closed Production Deploys**: Updated our GitHub Actions + Helm release pipeline so any schema or connector deployment automatically aborts and rolls back if post-deploy offset advancement checks fail.
