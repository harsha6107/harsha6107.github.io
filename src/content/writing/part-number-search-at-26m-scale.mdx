Standard full-text search engines are tuned for natural language prose. Their default analyzers split on whitespace and punctuation, strip symbols, lowercase stems, and rank documents by BM25 term frequency.

In an industrial procurement catalog of **26 million SKUs**, that default behavior fails on almost every query.

When we audited search logs and SKU patterns across Peregrin's multi-tenant catalog, we found a startling distribution: **roughly 77% of all SKUs contain at least one forward slash (`/`)**, alongside hyphens, decimal points, and fractional thread callouts (`3/8-16x1-1/2`, `SKF-6204-2RS1/C3`).

## Failure Mode 1: The Slash Tokenization Trap

Under Elasticsearch's `standard` analyzer, a buyer searching for `6204-2RS/C3` emits the token stream `["6204", "2rs", "c3"]`. Meanwhile, a query for `62042RSC3` (typed from a worn packing slip or barcode scanner that strips delimiters) emits `["62042rsc3"]`—producing **zero token overlap** with the indexed part number.

Conversely, when a buyer searches a fractional fastener like `1/4-20`, splitting on `/` and `-` produces single-digit tokens `"1"`, `"4"`, and `"20"`, matching millions of unrelated parts and blowing up postings list traversal latency.

### Designing a 4-Tier Analyzer Cascade

Instead of forcing one analyzer to solve exact lookup, delimiter-insensitive matching, prefix autocomplete, and OCR typo recovery simultaneously, we indexed every part number across four specialized sub-fields:

```json
{
  "settings": {
    "analysis": {
      "char_filter": {
        "strip_delimiters": {
          "type": "pattern_replace",
          "pattern": "[^a-zA-Z0-9]",
          "replacement": ""
        }
      },
      "normalizer": {
        "sku_exact_folded": {
          "type": "custom",
          "filter": ["lowercase", "asciifolding"]
        }
      },
      "analyzer": {
        "sku_alnum_compact": {
          "tokenizer": "keyword",
          "char_filter": ["strip_delimiters"],
          "filter": ["lowercase"]
        },
        "sku_structural_prefix": {
          "tokenizer": "whitespace",
          "filter": ["lowercase", "edge_ngram_2_20"]
        }
      }
    }
  }
}
```

At query time, a `dis_max` + `function_score` query evaluates all four representations in parallel:

1. **Exact Folded Keyword (`boost: 12.0`)**: Preserves slashes and hyphens verbatim (`1/4-20` matches `1/4-20` before anything else).
2. **Alphanumeric Normalized (`boost: 8.5`)**: Collapses `6204-2RS/C3` and `62042RSC3` to the same canonical token `62042rsc3`.
3. **Structural Edge N-Gram (`boost: 4.0`)**: Handles progressive prefix typing without costly leading wildcards.
4. **Bounded Fuzzy Fallback (`boost: 1.5`)**: Applies `fuzziness: AUTO:4,7` only on tokens of length ≥ 4, tied-broken by `log1p(tenant_popularity)`.

## Failure Mode 2: 100,000-Bucket Aggregations

Relevance was only half the equation. Every search request also computed sidebar facet counts across manufacturers and categories—requesting `size: 100000` buckets per aggregation. On broad prefix queries matching 500K+ documents, coordinator nodes allocated massive priority queues just to serialize buckets the UI never rendered.

By capping facet aggregations at **500 buckets** and moving deep manufacturer lookup to a dedicated prefix-filtered endpoint, we cut per-query aggregation bucket footprint by **99.5%**.

## Failure Mode 3: Silent Record Drops in 26M-Doc Syncs

No ranking function can surface a document that was silently dropped during ingestion. Root-causing missing SKUs in our 26M-document index revealed **6 separate pipeline defects**—most notably a batch job attempting to send **70,000+ SKUs in a single `_bulk` HTTP payload** and uninspected item-level error arrays in bulk responses.

Rebuilding the pipeline around **keyset pagination** (`WHERE (updated_at, sku_id) > (@lastTs, @lastId)`), dual-bounded chunks (**~1,000 documents or 5 MB max**), **2x write concurrency**, **15-minute incremental deltas**, and **count-verified blue/green alias swaps** eliminated silent record loss permanently.
